# Файл конфигурации 1Cv7.MD и внешний отчёт .ert

© 2026 Виталий Липатов. Распространяется на условиях GPL, см.
[licenses/license.txt](licenses/license.txt).

Документ собран при переносе GComp 3 по исходникам GComp
(`src/metadata/NameTable.cpp`, `src/storage`), разбору 431 конфигурации и
внешнего отчёта и опытам с тестовыми MD. Сведения о GUIDData, TagStream, пароле и временных файлах взяты
из статьи Фёдора Езеева «Структура файла 1cv7.md» (2003–2005, копия — в
репозитории trdm/GComp, `doc/MdStruct/PageAll.htm`) и проверены на корпусе,
где это возможно. Форматы отдельных потоков описаны в
[metadata.md](metadata.md), [dialog-forms.md](dialog-forms.md),
[interfaces.md](interfaces.md), [moxcel.md](moxcel.md) и
[rights.md](rights.md).

## Контейнер

`1Cv7.MD` и `.ert` — составной файл OLE (Compound File Binary, MS-CFB):
дерево хранилищ (каталогов) и потоков. Каждое хранилище содержит поток
`Container.Contents` со списком своих элементов:

```
{"Container.Contents",{"<Тип>","<Имя потока или хранилища>","<Название>",""}, ...}
```

Четвёртое поле во всех просмотренных файлах пустое. 1С перечисляет элементы в
своём порядке, а не в порядке каталога CFB (тот сортирует имена по длине), и
заканчивает поток переводом строки. GComp 3 записывает этот порядок так же.
Хранилища и потоки, на которые не ссылается ни один `Container.Contents`, —
остатки удалённых объектов; 1С их не читает, и GComp их не выгружает. По
наблюдению Езеева, такие остатки особенно часты в `Journal`: формы журналов с
ID самого журнала, видимо, со времён 7.0, когда у журнала была одна форма.

Модули (`MD Programm text`) и картинки сжаты raw deflate (zlib, windowBits −15).
1С пишет их zlib 1.0.4 (`zlibeng.dll`, уровень 4, memLevel 9). Другие
версии zlib сжимают иначе, но распакованный текст тот же, и 1С такие потоки
читает. За концом сжатых данных у некоторых потоков лежит мусор буфера 1С.

Потоки метаданных и диалогов начинаются с длины текста, записанной как
`CString` MFC: длина меньше 0xFF — 1 байт, меньше 0xFFFE — `FF` и 2 байта,
иначе `FF FF FF` и 4 байта, little-endian. Подробно — в
[dialog-forms.md](dialog-forms.md#заголовок-потока).

`Container.Profile` выглядит так:

```
{
{"MoxelName","",""},
{"MoxelPos","0",""},
{"UUID","D41D8CD98F00B204E9800998ECF8427E",""},
{"Entry","1",""},
{"MoxelNextMode","1",""}}
```

1С создаёт его, когда объект открывают на редактирование; по Езееву, без
него конфигурация работает. GComp 3 не выгружает его, когда он совпадает с
тем, что создаётся при сборке.

Пустая таблица moxcel занимает 147 байт (в формате 7.5 — 139). В корпусе
таких 4275 и 453 из 12 699 таблиц; ключ `--no-empty-mxl` их пропускает.

### Интерфейсы и права

`UserDef/Page.1` содержит хранилище `Page.<N>` на каждый интерфейс; тип
записи — `UsersInterfaceType` (основной интерфейс) или
`SubUsersInterfaceType` (подчинённый), название — имя интерфейса. В
хранилище интерфейса лежат потоки `Commands` (команды), `Page.1` (меню,
MenuEditorType) и `Page.2` (панели, ToolbarEditorType); у подчинённого
интерфейса — только `Commands`. Форматы — в [interfaces.md](interfaces.md).

`UserDef/Page.2` содержит потоки `Page.<N>` с наборами прав, формат — в
[rights.md](rights.md).

## Внешний отчёт .ert

Внешний отчёт — тот же составной файл без хранилищ, все потоки в корне:

| Поток | Тип в Container.Contents |
| --- | --- |
| `Main MetaData Stream` | MetaDataHolderContainer |
| `Dialog Stream` | DialogEditor, «Dialog Form» |
| `MD Programm text` | TextDocument, «Module text» |
| `Inplace description` | MetaDataDescription, «Описание» |
| `Page.<N>` | Moxcel.Worksheet, название таблицы |
| `Container.Profile` | |

Поток метаданных внешнего отчёта содержит те же записи, что и у
конфигурации, но почти пустые; ID в форме отчёта относятся к той
конфигурации, в которой отчёт создан. Ключ `--truncate-mms` заменяет его
при сборке пустым. За текстом потока метаданных внешнего отчёта стоит байт
`00`, не входящий в длину из заголовка (во всех 4462 проверенных
внешних отчётах); у конфигурации его нет.

*2026:* что кладёт Конфигуратор 7.70.027 в поток метаданных, когда отчёт
конфигурации сохраняют командой «Действия → Внешний отчет (обработка) →
Сохранить как внешний отчет (обработку)…» (сравнение с потоком
конфигурации; конфигурация 0b58d5ce корпуса и пустая тестовая):

- без изменений: `MainDataContDef`, `TaskItem`, `RecalcRules`,
  `Document Streams`;
- пустыми записями: `GenJrnlFldDef`, `DocSelRefObj`, `DocNumDef`, `Consts`,
  `Registers`, `Journalisters`, `ReportList`, `CJ`, `Algorithms`,
  `CalcVars`, `Groups`;
- справочники (`SbCnts`), документы, перечисления — все объекты с
  собственными параметрами, но без реквизитов (`Params`, `Head Fields`,
  `Table Fields`), значений (`EnumVal`) и форм (`Form`);
- `Calendars` — только `HolidaysDef`;
- `Buh` — параметры бухгалтерии без реквизитов счетов (`AccParams`), счетов
  в планах (`Accounts`; сами планы остаются), реквизитов проводки
  (`ProvParams`), видов субконто (`SbKind`) и списков форм (`Form`);
  журнал операций со своей формой остаётся;
- CRC пересчитан.

Картинки, на которые ссылается форма отчёта, копируются в собственное
хранилище `Picture` внешнего отчёта под новыми номерами `0x1F000001`,
`0x1F000002`… (ссылки в форме заменяются), галерея `Gallery` строится
заново с миниатюрами только этих картинок. Картинки есть в формах 785 из
1920 отчётов и 674 из 2307 обработок корпуса. Форму Конфигуратор при этом
пересохраняет со своими отступами клиентской области (элементы сдвигаются
на разницу, см. [dialog-forms.md](dialog-forms.md)).

Подробности проверены на файлах, сохранённых Конфигуратором 7.70.027 в
Windows 7 из конфигураций 0b58d5ce (семь отчётов и обработок с 1, 2, 3, 8 и
13 картинками) и 2338f880 (два, галерея 24 бита на точку) и из копий
0b58d5ce с подставленными в галерею проверочными
картинками (BMP 1, 4, 8 и 24 бита от 10×10 до 336×15 и 180×180, иконки 4 и
8 бит 16, 24, 32 и 48 точек):

- Номера раздаются при обходе элементов формы с последнего: картинка
  получает следующий номер там, где встретилась впервые. Где в этом
  порядке картинка самой формы, не проверено (в проверенных формах её нет).
- Потоки картинок копируются как есть, байт в байт (и сжатые данные тоже).
  Так со всеми картинками настоящих конфигураций: их туда добавлял сам
  Конфигуратор. Картинки, подложенные в галерею в обход него (иконки не в
  его виде, WMF с обычным заголовком), Конфигуратор сохраняет заново
  (иконки — 4 бита, 16 цветов; у WMF заголовок `0,0,1,−2340` и метафайл
  пересобран) и миниатюру иконки рисует по новой; GComp пишет их как есть.
- Галерея пишется одинаково, какой бы ни была галерея конфигурации (у
  2338f880 — 24 бита на точку и шаг роста 48): список картинок `IL`
  версии `0x0101` с клетками 80×80 по 4 в ряд, 16 бит на точку
  (`ILC_COLOR16`), шаг роста 8, без цвета фона и наложений; число картинок
  и ёмкость — сначала 10, а картинка, которая не поместилась, делает её
  равной своему номеру + 8 (10, 19, 28…; так же и у галереи конфигурации:
  56 картинок — 64); полоса миниатюр на всю ёмкость, хвост — метка
  `0xFF000001`, число и номера картинок, счётчик `0x0F000000` + число
  картинок и пустой список имён `{}`.
- Миниатюры Конфигуратор рисует заново из картинок, в клетке 80×80, 16 бит
  на точку (5:5:5, младшие биты цвета отбрасываются), на белом:
  - картинка вписывается в клетку с сохранением пропорций и ставится по
    центру; сторона меньше 16 точек делается 16; поле с каждой стороны —
    `ceil((80 − размер) / 2 − 1/2)` (половина округляется вниз), справа и
    снизу такое же;
  - точка миниатюры `i` берёт точку картинки `(2i + 1)·S / (2D)` (под своей
    серединой; `S` — размер картинки, `D` — размер в клетке), без
    смешивания цветов;
  - если по обеим осям картинка отличается от своего размера в клетке не
    больше чем на точку (79×79, 81×81, 81×40…), она не растягивается, а
    копируется с левого верхнего угла, последняя точка повторяется;
  - иконка рисуется так же, через маску: белый AND маска XOR цвет (у
    прозрачных точек иконок 1С цвет 0, они белые);
  - метафайл WMF (placeable, `D7CDC69A`) вписывается по размеру из
    заголовка (`right − left`, `bottom − top` со знаком; заголовок,
    который пишет Конфигуратор, `0,0,1,−2340`, даёт полосу 80×16
    посередине; ширина не больше 0 — пустая клетка) и обрезается по своей
    рамке; точки окна переводятся в рамку с точностью 1/16 точки и затем
    округляются; многоугольник по целым вершинам закрашивает точку, если
    она в `[левое пересечение, правое пересечение)` своей строки (ребро
    считается от верхнего конца, без нижнего), ALTERNATE или WINDING;
    линия пером в 1 точку — без последней точки, по малой оси половина
    округляется вниз. GComp рисует так окна, перья и кисти (сплошные и
    пустые), Polygon, PolyPolygon, Polyline, MoveTo/LineTo и Rectangle с
    пером; с другими записями берёт миниатюру из галереи конфигурации.
    Проверено в Windows на обоих метафайлах конфигураций корпуса (в
    выгрузке корпуса они встречаются 52 раза) и семи проверочных:
    совпадают все.

  Так нарисованы 436 из 464 миниатюр в 181 внешнем отчёте корпуса с
  галереей; остальные сохранены на других машинах: серый или
  `ffff`-белый фон (другая схема цветов или экран 5:6:5), 24 бита на точку,
  точки на самой границе соседних точек картинки взяты иначе.
- Ссылка формы на картинку, которой нет в галерее конфигурации или у
  которой нет своего потока (потерянная картинка), остаётся прежней.
- В галереях конфигураций старых выпусков в хвосте нет метки
  `0xFF000001`: число картинок стоит сразу после полосы миниатюр
  (11db347a), а точки бывают и по 4 бита.
- OLE-объекты в таблицах (`CSheetCntrItem`) Конфигуратор сохраняет заново
  со временем сохранения внутри, такие листы с конфигурацией не совпадают.

Под Wine Конфигуратор пишет иначе: резервный байт палитры BMP `0xFF`,
иконки с палитрой переписаны в 32 бита на точку с альфой 0 (миниатюры у
них чёрные), уменьшенные картинки — со смешиванием точек по AND. GComp
пишет так, как в Windows. Иконки 32 бита на точку Конфигуратор в Windows
сохранить не может (падает или пропускает картинку). Под Wine и
миниатюры WMF отличаются: вершины многоугольников округляются сразу до
точки, рисунок не обрезается по рамке. Ошибки Wine заведены:
https://bugs.etersoft.ru/show_bug.cgi?id=19981 (собирательная).

Корень внешнего отчёта: `Container.Contents` — запись `Main MetaData
Stream`, записи рабочей книги отчёта (с названиями листов из конфигурации)
и после модуля `{"MetaDataDescription","Inplace description","Описание",""}`;
хранилище `Picture` в нём не упоминается, его собственный `Container.Contents`
содержит только `Gallery`. Описание берётся из
`TypedText/UserHelp_Number<ID>` как есть; без описания — пустой сжатый
поток.

GComp с ключом `--ert` пишет такие файлы при разборе конфигурации
(`src/metadata/ExportERT.cpp`).

Единственный лист рабочей книги без своего имени 1С называет
`Moxel WorkPlace` (`{"Moxcel.Worksheet","Page.1","Moxel WorkPlace",""}`);
GComp разбирает его в `Таблица.mxl` без `ПорядокОбъектов.ord` и пишет это
имя обратно. Модуль обращается к такому листу как к «Таблица»:
`ИсходнаяТаблица("Таблица")` в 1С 7.70.027 его находит (обработка
«ПечатьПрайса» ТиС, 2026-11-13); названный лист (`"Таблица"`, как у
«ДвиженияДокумента») — по своему названию.

## GUIDData и TagStream

`GUIDData` — история сохранений конфигурации, по которой 1С решает, является
ли загружаемая конфигурация потомком текущей. Поток — 32-битное число `N` и
`N` записей по 16 байт (GUID); во всех 31 потоке корпуса длина ровно
`4 + 16·N`. Иначе говоря, 20 байт заголовка (число и первый GUID) и
`N − 1` записей. По Езееву, при каждом сохранении новая запись добавляется
в начало (со смещением 20), а последняя удаляется, когда записей 2000; так что
после 2000 сохранений 1С перестаёт узнавать потомков. В корпусе у 22 из 30
конфигураций поток ровно 32 020 байт (2000 записей) и первое слово 2001.

Из этого следует: если сохранить конфигурацию, загруженную как изменённую, у
неё будет другая история, и конфигурация, сделанная из исходной, при загрузке
окажется «не потомком». Для разработки в git поток можно не хранить, но его
история показывает каждое сохранение.

`TagStream` хранит закладки «Автор» и «Заставка» свойств конфигурации:
сведения об авторе с логотипом, название и заставку. Поток зашифрован RC4 с
тем же 16-байтным ключом, что и зашифрованный `Main MetaData Stream`
(`60 46 D2 72 64 25 03 00 09 89 00 C0 DD 3B E6 36`), и сцеплением: байт
шифротекста = байт текста XOR байт RC4 XOR предыдущий байт шифротекста, а
для первого байта — `S[0]` после расписания ключа. 1С меняет байты состояния
RC4 местами через XOR, поэтому обмен байта с самим собой (`i = j`) его
обнуляет; без этой особенности расшифровка ломается после первых сотен
байт. Алгоритм сверен с MDPassWorks (D. Dreytser) и проверен на всех 30
потоках корпуса: расшифровка и обратное шифрование дают те же байты.

Внутри — строка MFC `CString` (длина как в [moxcel.md](moxcel.md)) со
скобочным текстом 1С, в CP1251:

```
{{"_HASH_STRING_","D41D8CD98F00B204E9800998ECF8427E"},
 {"_AUTOR_SHOR_STRING_","Комплексная конфигурация, редакция 4.5"},
 {"_AUTOR_LONG_STRING_","..."},
 {"_AUTOR_LOGO_INDEX_",""},
 {"_AUTOR_SPLASH_INDEX_","*    ,P!  !I ..."},
 {"_AUTOR_LOGO_PICTURE_POS","..."}}
```

(переносы строк добавлены для чтения). Кавычки внутри значений удвоены.
`_HASH_STRING_` — свёртка пароля конфигурации на основе MD5 (по
MDPassWorks); `D41D8CD98F00B204E9800998ECF8427E` — MD5 пустой строки, то
есть пароля нет. У 5 конфигураций корпуса значение короткое (`A208`,
`82DC`), хотя они не зашифрованы; что оно значит, не выяснено. Логотип (в корпусе 64×64) и заставка (460×105) — картинка DIB
(`BITMAPINFOHEADER`, палитра, точки; 8 бит на точку) в кодировке, похожей
на UU: каждые 4 символа (код − 0x20) дают 3 байта. Последнего тега
в части потоков нет. В 6 потоках корпуса после строки остаются лишние байты
— хвост прежнего, более длинного содержимого.

GComp выгружает оба потока как есть и собирает из них, а рядом для
просмотра пишет `GUIDData.txt` (GUID по строке), `TagStream.txt`
(`СвёрткаПароля`, `КраткаяИнформация`, `РазвернутаяИнформация` — по
названиям полей диалога «Автор конфигурации», размеры и CRC32 картинок,
`ПоложениеЛоготипа`) и картинки `TagStream.Логотип.bmp` и
`TagStream.Заставка.bmp`. Эти файлы при сборке не читаются.

## Пароль и временные файлы

По Езееву, штатный пароль конфигурации шифрует только поток метаданных и
глобальный модуль; формы, модули форм и таблицы остаются открытыми. В
единственном зашифрованном файле корпуса зашифрован `Main MetaData Stream`, а
глобальный модуль распаковывается как обычно. GComp зашифрованные файлы не
разбирает.

Этот файл — пакет обновления («Бухгалтерский учет, редакция 4.5»,
7.70.532), пароля у него нет (`_HASH_STRING_` — MD5 пустой строки). Поток
метаданных зашифрован не так, как `TagStream`: ни ключ `TagStream`, ни ключ
глобального модуля (MDPassWorks) не дают известного начала потока (длина
`CString` и `{\r\n{"MainDataContDef"`). Признак шифрования — CLSID
`0af60370-754e-11d2-9f21-008048da120f` у хранилища. Сам алгоритм не
разобран.

Во время работы Конфигуратор держит текущую конфигурацию в каталоге TEMP под
именем `~md??.tmp` (вместо `??` — шестнадцатеричные цифры, по копии на
каждый запущенный Конфигуратор). Сообщения вида «Плохой путь» с путём
вроде `D:\temp\~mdAB.tmp\Subconto\Subconto_Number33\WorkBook\Dialog Stream` указывают
на испорченный поток внутри MD: здесь — на форму элемента справочника с
ID 33. Там же остаются копии после сбоев.

## Main Metadata Stream

Текст списков в фигурных скобках, CP1251, с `\r\n` перед вложенными
списками. Корневой список — `{"MainDataContDef", ...}`, затем `TaskItem`,
списки объектов (см. [metadata.md](metadata.md)) и в конце запись `CRC`.

### MainDataContDef

```
{"MainDataContDef","<NextID>","<Версия>","<UnknownID>"}
```

| № | Поле | Описание |
| ---: | --- | --- |
| 1 | NextID | Следующий свободный ID объекта |
| 2 | Версия | Версия формата метаданных. В корпусе — 10011 у всех 30 конфигураций и 399 внешних отчётов, 10010 у одного отчёта |
| 3 | UnknownID | Во всех 430 читаемых файлах корпуса — 7120 |

В версии 10010 у плана счетов две маски кода счёта; GComp 2.2.15 при сборке
понижал версию до 10009 и терял первую маску.

### TaskItem — описание конфигурации

Свойства задачи, в дереве GComp 3 — `ОписаниеКонфигурации.yaml`:

| № | Свойство GComp 3 | Описание |
| ---: | --- | --- |
| 1 | ID | ID |
| 2 | Идентификатор | Имя конфигурации |
| 3 | Комментарий | Комментарий, часто номер релиза |
| 4 | Синоним | Синоним |
| 5 | Пароль | Пароль конфигурации |
| 6 | Основной язык | Основной язык конфигурации |
| 7 | Журнал подчинённых документов | ID журнала, отмеченного «Использовать как журнал подчиненных документов» |
| 8 | Непосредственное удаление | Удаление объектов без пометки |
| 9 | Способ округления | Округление при вычислениях |
| 10 | Полный журнал документов | ID журнала, отмеченного «Использовать как полный журнал документов» |

Параметры 7 и 10 — флажки в диалоге свойств журнала документов; в потоке они
хранятся в описании задачи. Значение бывает пустым или `0`, если журнал не
выбран.

### CRC

Для версии выше 10010 последний элемент корня — `{"CRC","N"}`. Без него или
с неверным значением 1С не открывает конфигурацию («Общая файловая ошибка при
доступе к ...\1Cv7.MD\Metadata\Main MetaData Stream»).

`N` считается по тексту потока, пересохранённому без переводов строк (вне
кавычек), из которого удалён элемент `CRC`. Для каждого байта `c` (signed
char) с номером `i`:

```
b3 += c;  b1 ^= c % 3;  b2 ^= c % 7;  b0 ^= (signed char)(i + c) % 11;
N = b0 | b1 << 8 | b2 << 16 | b3 << 24     (печатается как беззнаковое)
```

Остатки — как у деления в C (знак делимого). GComp 3
вычисляет CRC при сборке: потоки метаданных корпуса, собранные им, совпадают
с исходными, а MD с изменённой конфигурацией открывается в 1С.
